_Run the worker on the Mistral platform: one command deploys it, one more sends it work_

# Overview

A managed deployment hosts the worker for you: the platform builds the Docker image from the repo, runs it, and reports status. The worker connects out to the Mistral-hosted Temporal service, so there is no cluster to run and no port to expose.

## Deploy: `mistral apps deploy`

```bash
git push
mistral apps deploy
```

Run from the app root after `mistral login`. The workflows capability marks the `worker` module `"platform": "workflows"`, and `mistral apps deploy` runs that module as a managed deployment. It:

- names the deployment `<app>-<module>`, where `<app>` is the platform app's name (`--name` on the first deploy, or else the directory name), for example `my-app-worker`, and prints it;
- builds the pushed commit on Mistral Cloud from `deploy/docker/Dockerfile.worker` at the repo root, using its last stage;
- sets `DEPLOYMENT_NAME` to that name on the app's other deployed modules, so the deployed API dispatches to it;
- waits until the new worker has registered, and fails with the platform's message if the build or rollout fails.

The first run creates the deployment. Later runs update it to the new commit, including a moved origin or renamed repository, and the old replica keeps serving until the new one is up. A run on a commit that is already live does nothing. An app declares at most one such worker.

The deployment name is per app, so everyone who deploys the same app updates the same deployment. A local worker keeps polling the per-user `DEPLOYMENT_NAME` from `.env`, so it never takes work meant for the managed one.

### What the Build Needs

Mistral Cloud builds the image. An app whose Python dependencies all resolve from public PyPI builds as-is. An app with a dependency on an authenticated package index does not, because the build cannot read the credential it needs to install from it.

A dependency bound to an authenticated index needs its credential at build time. Bind it as a secret under the deployment's `backend_spec.secrets`: each binding's `env_var_name` reaches the build as a Docker build arg, and the `Dockerfile` opts in by declaring a matching `ARG`. The shipped `Dockerfile.worker` reads its index credential from a BuildKit secret mount, which Mistral Cloud does not provide, so add the two matching `ARG` declarations to the build stage and bind the secret under those names. The `env_var_name` to use is the one the app's `tools/uv.sh` exports for the index's `[[tool.uv.index]]` entry, and the value is that index's credential.

`mistral apps deploy` does not set bindings. The `mistralai` SDK cannot send them either (its backend spec has only `build_directory` and `dockerfile_path` through 2.10.1), so set them with a `PATCH` to `/v1/workflows/deployments/{name}`. Each binding names a workspace secret, which the platform resolves at build time, so create the secrets first. Stored as workspace secrets, they bind like this:

```bash
curl -X PATCH "https://api.mistral.ai/v1/workflows/deployments/my-app-worker" \
  -H "Authorization: Bearer $MISTRAL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"spec": {"backend_spec": {"type": "koyeb", "secrets": [
        {"env_var_name": "UV_INDEX_<NAME>_USERNAME", "reference": "secret:workspace:<INDEX_USER>"},
        {"env_var_name": "UV_INDEX_<NAME>_PASSWORD", "reference": "secret:workspace:<INDEX_TOKEN>"}
      ]}}}'
```

Send the complete list, because it replaces the current bindings. `mistral apps deploy` leaves existing bindings in place when it updates the deployment. Build args persist in the image's layers and history, so bind a credential you can rotate.

The repo must be readable by the platform's GitHub App connector. A push target the connector cannot see fails with `github_repository_not_found`, which is an access grant question rather than a defect in the app.

## Send It Work

Start a run on the deployment with the app's configured client. `get_client()` targets `WORKFLOWS_BASE_URL` with the `MISTRAL_API_KEY` from the root `.env`, and encrypts the input when payload encryption is on; the `mistral login` session does not work here.

```python
import asyncio

from mistralai_capabilities.workflows.client import get_client


async def main() -> None:
    client = await get_client()
    run = await client.workflows.execute_workflow_async(
        workflow_identifier="hello_world",
        input={"name": "World"},
        deployment_name="my-app-worker",
        wait_for_result=True,
    )
    print(run.result)


asyncio.run(main())
```

Save it as a file and run it from the app root with `uv run python <file>`. With `wait_for_result` the response carries the result once the execution finishes, and `timeout_seconds` bounds the wait; without it, the call returns as soon as the execution is accepted. The platform validates the input against the schema the deployed worker registered: a bad payload gets a 422 and no execution starts, and an unknown workflow name gets a 404.

## Checking on It

The deployment's state is in the platform API:

```python
import os

from mistralai.workflows.client import get_mistral_client

client = get_mistral_client(api_key=..., server_url=os.environ.get("MISTRAL_BASE_URL"))
d = client.workflows.deployments.get_deployment(name="my-app-worker")
print(d.managed.status.phase)              # pending -> building -> running
print(d.managed.status.deployed_revision)  # commit SHA the live worker is running
```

Pass `MISTRAL_BASE_URL` as `server_url`: the app's platform calls target `env.mistral_base_url`, while `get_mistral_client()` without a `server_url` reads the SDK's `SERVER_URL`, which an app does not set. Unset, both fall back to the public API host.

A build that fails lands on `build_failed`, with the reason in `status.message`. Build logs are not exposed through the API yet; `get_deployment_logs` returns the running worker's logs, not the build's.

## The Full Loop

```bash
# 1. ship the current commit and wait for it to roll out
git commit -m "wf: change the workflow" && git push
mistral apps deploy

# 2. prove it runs: start hello_world as in "Send It Work"
```

Every later change is step 1 again.

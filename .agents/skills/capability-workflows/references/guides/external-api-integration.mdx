# External API Integration

Use this guide when a workflow **activity** must call an external HTTP API or SDK directly. Prefer a workspace [connector](connectors.mdx) whenever one can reach the API — see [Connector first](#connector-first) for the residual cases.

## Connector first

The workspace HTTP connector is the default path; a direct activity is only for the residual cases a connector cannot cover:

- **Credentials the platform cannot hold** — tokens minted by the user's own sign-in flow, user-held secrets.
- **Auth schemes or lifecycles the gateway does not support** — proprietary token exchanges, request signing, mTLS.
- **APIs unreachable from the deployment's connector-gateway egress** — the gateway's network position may differ from the workers' (network policies, APIs reachable only from the workers' network).
- **Per-request control the connector abstraction does not expose** — custom idempotency keys, custom `Retry-After` handling.

If none of these apply and a workspace connector covers the operation, use the [connector guide](connectors.mdx) instead.

## Choose the scenario

First ask **whose permissions the API call should use**, then **where the API credential comes from**. A user token lets the app act as that person; a service identity lets the app act as a technical account, even when nobody is logged in. (For the workflow-level identity decision — worker identity vs `on_behalf_of` — see [Identity](../identity.md).)

| Scenario                            | Typical use case                                                                         | How the activity authenticates                                                       |
| ----------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 1. Signed-in user                   | An assistant reads the current user's own profile.                                       | Receives that user's token through encrypted arguments.                              |
| 2. Fixed service credential         | A scheduled integration reads business records with a dedicated technical account.       | Reads a stored API key or Basic Auth credentials from runtime secrets.               |
| 3. Service obtains temporary tokens | An enterprise data platform issues short-lived access tokens to registered applications. | Uses a client ID/secret to obtain a token; a supported SDK can acquire and renew it. |

Scenarios 2 and 3 use the same kind of identity, but have different token lifecycles.
**Bearer** describes an HTTP authorization header, not a scenario: either a user's
token, a fixed service key or a temporary service token can use it. Likewise, an SDK
does not determine the scenario; check which identity and authentication flow it uses.

Check the external API's contract: identity, permitted operations, worker network
access and quota. Create **one typed `async def` activity per API operation**
(`get_account`, `list_transactions`, `update_address`), with narrow business inputs
and outputs. Keep HTTP, SDK calls and secret access inside activities. Do not expose
an arbitrary URL/method/headers tool to the model. Use async I/O; an `async def`
wrapper does not make a synchronous SDK nonblocking. Offload a sync-only SDK with
bounded concurrency and its own transport timeouts.

## Encrypt credentials and sensitive data

**Encrypt tokens and sensitive API data in workflow/activity inputs and outputs.** Both
SDK modes are valid:

- **`full`** encrypts the entire payload. Prefer it when the payload contains sensitive
  data throughout or when field-by-field classification is uncertain.
- **`partial`** encrypts only fields marked with `EncryptedStrField`. Use it when every
  sensitive field is identified and marked, including returned business data.
  Unmarked fields remain readable; marking only the access token is insufficient
  if the response also contains personal or confidential data.

For the complete setup — the `mistralai[workflow-payload-encryption]` extra, the worker
environment variables, key rotation and retention, standalone-client configuration, and
payload-offloading verification — see the [payload encoding guide](payload-encoding.mdx)
and the [current encryption documentation](https://docs.mistral.ai/studio/workflows/building-workflows/encryption).
Keep credentials and sensitive data out of logs, exception details, telemetry, model
prompts and workflow metadata such as IDs/search attributes; do not assume payload
encryption covers them.

## Scenario 1: act as the signed-in user

Use this when the external API must enforce the logged-in person's permissions.
For example, a banking assistant reads the current user's accounts. The application
already has their API token from its authentication flow; the activity uses that
token rather than authenticating as a separate technical account.

1. Authenticate at the application edge and authorize the resource from trusted
   session context. Inject the token there, never from model-generated arguments.
2. Pass it as an `EncryptedStrField` through the encrypted workflow input and
   activity arguments. Unwrap `.data` only inside the consuming activity.
3. Attach it to that request's authorization header, never a shared client's
   default headers. Return only required business fields, protected by the chosen mode.

If a scoped credential service already exists, pass its reference and resolve the
token inside the activity, enforcing user/tenant binding. Handle expiry through the
supported refresh flow or reauthentication; never fall back to a service identity.

## Scenario 2: use a fixed service credential

Use this when the integration is given a dedicated API key or Basic Auth account.
For example, a nightly job reads business records without a user session. The stored
credential is sent on each API request; this integration does not exchange it for a
new access token. Rotate it through the secret mechanism.

1. Store credentials in the deployment's runtime secret mechanism with the minimum
   permissions required. Authorize the caller's business operation separately;
   a service account does not enforce the signed-in user's permissions for you.
2. Resolve credentials inside the activity and attach them according to the API
   contract: for example, `httpx.BasicAuth` or a request-specific bearer header.
3. Pass only business inputs through the activity boundary; return minimal business
   results. Do not introduce an authentication activity that returns an access token.

Credentials must remain resolvable after a worker restart. Basic Auth and static
keys still require verified HTTPS; never place credentials in URLs.

## Scenario 3: obtain a temporary service token

Use this when the integration is registered as an application and supplied a
client ID/secret. For example, a job queries an enterprise data platform whose SDK
authenticates the application and renews short-lived tokens. The business API receives
the temporary token, not the long-lived client secret; no user login is involved.

Apply scenario 2's service authorization and secret-storage rules. Inside the business
activity, initialize the supported client with runtime credentials and least-privilege
scopes. Let its documented authentication flow acquire and renew tokens; otherwise
implement the API's specified exchange. Keep both credentials and acquired tokens
inside the activity-side integration layer. Pass only business inputs through the
workflow and return encrypted business data.

```text
workflow: business input
    -> activity: load client credentials -> SDK obtains/renews token -> query API
    <- business result, with sensitive fields encrypted
```

Follow the actual SDK's documentation for authentication, refresh and async transport;
do not invent a universal SDK method. The reusable distinction from scenario 2 is the
token-acquisition/renewal step, which happens inside the same business activity.

## Example 1: read the user's profile

The example below is validated with `mistralai-workflows` 3.16.0 and works
with either configured encryption mode; it implements scenario 1, and the
scenarios 2 and 3 notes below follow the same shape.
User-token arguments and personal data are marked for `partial`; `full` also protects them.
Keep those wrappers across workflow/activity boundaries; unwrap business results
only at the authorized point of use. The base URL is worker configuration, not
workflow input: the activity reads it from the worker's environment
(`ACME_API_BASE_URL`, e.g. `https://api.example.com`) and refuses anything but `https`,
so the token is only ever sent to the host the deployment configured. Replace the
endpoint, schema, the `acme` service prefix in the activity name, environment variable
and rate-limit key with the external API's own identifiers, so copied integrations do
not register the same activity name or share one rate-limit pool in the task workspace.
Use durable worker execution for real calls: SDK local execution can ignore
`non_retryable` errors and distributed limits. Use fake APIs for local tests.

```python
import os
from datetime import UTC, datetime, timedelta
from email.utils import parsedate_to_datetime
from typing import TYPE_CHECKING

import mistralai.workflows as workflows
from mistralai.workflows.models import EncryptedStrField  # Sandbox-safe SDK re-export.
from pydantic import BaseModel, ConfigDict, Field

if TYPE_CHECKING:
    import httpx


class GetProfileInput(BaseModel):
    model_config = ConfigDict(hide_input_in_errors=True)
    access_token: EncryptedStrField = Field(repr=False)


class Profile(BaseModel):
    model_config = ConfigDict(hide_input_in_errors=True)
    id: EncryptedStrField = Field(repr=False)
    display_name: EncryptedStrField = Field(repr=False)


API_RATE_LIMIT = workflows.RateLimit(
    time_window_in_sec=1, max_execution=10, key="acme-api"  # replace with your service
)


def _api_base_url() -> str:
    # Worker configuration, never workflow input: the token only goes to this host.
    base_url = os.environ.get("ACME_API_BASE_URL", "")
    if not base_url.startswith("https://"):
        raise workflows.WorkflowError(
            "api_base_url_not_configured_https", non_retryable=True
        )
    return base_url


def _retry_after(response: "httpx.Response") -> timedelta | None:
    value = response.headers.get("Retry-After")
    if value is None:
        return None
    try:
        delay = timedelta(seconds=int(value))
    except (ValueError, OverflowError):
        try:
            delay = parsedate_to_datetime(value) - datetime.now(UTC)
        except (TypeError, ValueError):
            return None
    return max(delay, timedelta(0))


def _require_ok(response: "httpx.Response") -> None:
    if response.status_code != 200:
        # 429, 502, 503 and 504 are transient; wait as long as the API asks.
        retryable = response.status_code in {429, 502, 503, 504}
        raise workflows.WorkflowError(
            f"api_http_{response.status_code}",
            non_retryable=not retryable,
            next_retry_delay=_retry_after(response) if retryable else None,
        )


def _parse_profile(response: "httpx.Response") -> Profile:
    _require_ok(response)
    try:
        body = response.json()
        return Profile(
            id=EncryptedStrField(data=body["id"]),
            display_name=EncryptedStrField(data=body["display_name"]),
        )
    except (ValueError, KeyError, TypeError):
        raise workflows.WorkflowError(
            "invalid_external_response", non_retryable=True
        ) from None


@workflows.activity(
    name="acme-get_my_profile",  # namespace the activity name per service
    start_to_close_timeout=timedelta(seconds=15),
    retry_policy_max_attempts=3,
    retry_policy_backoff_coefficient=2.0,
    rate_limit=API_RATE_LIMIT,
)
async def get_my_profile(params: GetProfileInput) -> Profile:
    import httpx

    base_url = _api_base_url()
    try:
        async with httpx.AsyncClient(
            base_url=base_url, timeout=10, follow_redirects=False
        ) as client:
            response = await client.get(
                "/me",
                headers={"Authorization": f"Bearer {params.access_token.data}"},
            )
    except httpx.RequestError:
        raise workflows.WorkflowError("api_unavailable") from None
    return _parse_profile(response)
```

## Example 2: read a profile with a service credential

Same read as example 1, but the worker mounts a fixed service credential (API
key or Basic Auth account) as a runtime secret and attaches it inside the
activity; only the business identifier crosses the activity boundary.

## Example 3: obtain a service token, then read a profile

Same read as example 1, but the external API's SDK owns token acquisition and
renewal inside the activity; the business API receives the short-lived token,
never the long-lived client secret.

## Limits, retries and verification

- **Rate limit:** scope the activity rate limit to the external API's budget, and
  account for every HTTP request an attempt makes (a token exchange plus a lookup
  is two requests; the activity limiter is not an HTTP-request cap). See
  [rate limiting](rate-limiting.mdx).
- **Retries:** set timeouts and retry policy per the API's contract; never retry
  429 or `Retry-After` responses sooner than the API allows: raise a retryable error
  with `next_retry_delay` set from `Retry-After`, as the example does, and keep the
  retry policy's attempts, any `schedule_to_close_timeout` and the workflow's timeout
  long enough to honor it. See
  [activities](activities.mdx) and
  [workflows exception handling](workflows-exception.mdx).
- **Writes:** retries and crash recovery can repeat side effects. Use the external API's
  idempotency key/reconciliation contract with a stable business operation ID.
  Even one configured attempt cannot rule out a successful write with a lost response.
- **Verify with synthetic data:** run the existing Workflows checks and a test execution
  (see [testing](testing.md)). Check user isolation, expiry, 429/transient errors and
  malformed responses. Inspect raw stored payloads with decoding disabled, plus
  logs/traces and serialized failures: token and response-data canaries must be
  absent. Test encryption on both inputs and outputs; a masked UI or a successful
  API call is not proof of encryption.
